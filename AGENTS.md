# AGENTS.md

Инструкции для AI-агентов, работающих с этим репозиторием. Сделано на основе CLAUDE.md, адаптировано под проект `tg-event`.

## О проекте

`tg-event` — proof-of-concept пайплайн для Telegram-афиши событий.

Что делает POC:
1. Читает недавние посты из списка публичных Telegram-каналов через Telethon.
2. Сохраняет сырые посты в JSONL-файлы (`data/raw/`).
3. Отправляет каждый пост в OpenRouter, валидирует строгий event-JSON, пишет распарсенные события в `data/parsed/` и в SQLite.

Один пост может породить ноль, одно или несколько событий (важно для дайджест-постов вида «5 событий на выходные»).

### Стек

- **Язык**: Python (ести国画, без фреймворков).
- **Telegram-клиент**: `telethon` — единственная внешняя зависимость (`requirements.txt`).
- **LLM-парсинг**: OpenRouter API, модели по умолчанию — `qwen/qwen3-next-80b-a3b-instruct:free` и fallback `qwen/qwen3.5-flash-02-23`. HTTP и работа с JSON — стандартная библиотека Python.
- **Хранилище**: SQLite (`data/tg_event.sqlite3`) — основной сторадж; JSONL в `data/raw/` и `data/parsed/` — отладочные экспорты.
- **Конфиг**: `.env` (читается собственной `load_dotenv`, без сторонних пакетов).
- **Тесты**: стандартная библиотека `unittest`, без внешних тест-фреймворков.

### Структура `tg_event/`

- `cli.py` — точка входа (`python -m tg_event.cli`), команды: `collect`, `parse`, `run`, `watch`.
- `config.py` — `Settings` (dataclass), `load_dotenv`, реквизиты и общие настройки.
- `collector.py` — чтение постов из Telegram через Telethon.
- `openrouter_parser.py` — отправка поста в LLM, валидация event-JSON.
- `event_schema.py` — схема события (поля, категории, статусы).
- `storage.py` — чтение/запись JSONL, `dated_path`.
- `database.py` — SQLite: `connect_database`, `init_database`, `save_parsed_rows`, `fetch_published_events`.
- `watcher.py` — фильтрация новых/изменённых постов и атомарная JSON-копия прогресса; основной прогресс хранится в SQLite (`watch_progress`).
- `event_updates.py` — применение переносов/отмен/уточнений с проверкой времени, источника и защиты ручных полей.
- `cleanup.py` — предварительный просмотр и очистка через 30 дней с резервной копией, еженедельный вызов из watcher.
- `channels.py` — управление каналами в SQLite, первая загрузка последних N постов и состояние проверок.
- `bot.py` — бот на Telethon, inline-кнопки периодов, выдаёт опубликованные события.

### Канал как сущность проекта

Канал — подключённый через админку публичный Telegram-канал, из которого агрегатор получает публикации о жизни города. Например, канал кофейни, площадки, организатора или городской афиши. Это источник публикаций: отдельный пост может оказаться новостью без события, а дайджест — содержать несколько событий. Одно мероприятие может упоминаться в нескольких каналах и при этом иметь одну карточку в боте.

У канала есть собственная запись `channel_settings` в SQLite. Она определяет, нужно ли читать канал, с чего начать сбор и что произошло при последней проверке. Добавление выполняется на странице `/channels` через авторизованный API `/api/channels`. `CHANNELS` из env не используется. Создание записи проверяет формат имени и отсутствие дубля; доступность канала проверяется сборщиком при следующем цикле.

Поля записи:

| Поле | Смысл |
| --- | --- |
| `username` | Уникальный идентификатор канала: имя без `@`, приведённое к нижнему регистру. Имя, `@имя` и публичная ссылка `t.me/имя` обозначают одну запись. |
| `enabled` | Включён ли сбор. Приостановка сохраняет уже собранные посты, события и прогресс. |
| `initial_posts` | Сколько последних постов взять при первом подключении: 1–1000, по умолчанию 20. Изменяется до фиксации границ первой загрузки. |
| `mode` | `recent` для новых каналов; `legacy` для ранее сохранённых записей со старым порядком сбора. Новые записи создаются в режиме `recent`. |
| `initial_start_id`, `initial_end_id` | Границы первой загрузки, фиксируемые один раз. Нижняя граница — ID перед самым ранним выбранным сообщением, верхняя — последний ID снимка. До начала значения NULL; у пустого канала обе границы равны 0. |
| `last_attempt_at` | Время последней попытки проверки, UTC. |
| `last_success_at` | Время последнего успешного чтения Telegram, UTC. Разбор и сохранение событий могут завершиться ошибкой даже после успешного чтения. |
| `last_error` | Безопасное описание последней ошибки подключения, чтения, разбора или сохранения, без реквизитов и токенов. |

Прогресс чтения хранится отдельно в `watch_progress`: последний обработанный ID и начальная дата по имени канала и профилю `--state`. API дополнительно вычисляет `last_message_id` (минимальную позицию всех профилей) и `initial_status`: `pending` — первая загрузка ожидается, `loading` — идёт, `complete` — завершена, `existing` — прежний режим сбора. Это вычисляемые свойства ответа, а не отдельные поля `channel_settings`. Активность `enabled` независима от стадии загрузки.

После первой загрузки watcher собирает всю очередь новых сообщений и проверяет отслеживаемые правки. `initial_posts` — разовая глубина подключения; размер порции чтения и лимит разбора за цикл задаются отдельно. Настройки каналов перечитываются каждый цикл; уже выполняющийся цикл может закончиться со старой настройкой. По умолчанию следующий цикл начинается через 30 минут после окончания предыдущего, интервал общий и задаётся `--interval`. Город и часовой пояс берутся из общих настроек проекта.

Связи с данными:

- `channel_settings` — управление сбором. Запись появляется при добавлении канала, даже если постов ещё нет.
- `sources` — происхождение сохранённых постов. Запись создаётся при сохранении поста; `raw_posts.source_id` ссылается на неё. С настройками канала она сопоставляется по имени, отдельного внешнего ключа между таблицами нет. Старая запись `sources` сама по себе не включает сбор.
- `raw_posts` — исходные сообщения канала; `events` — извлечённые карточки, `event_sources` — их связи с сообщениями. Поэтому приостановка канала не скрывает автоматически уже опубликованные события.
- `source_rules.json` — отдельно заданные связи каналов с организаторами/площадками для выбора основного источника. Добавление канала в админке само по себе не назначает ему такой приоритет.

При очистке сохранять настройки каналов и прогресс. Уже существующие записи, включая `legacy`, не пересоздавать и не сбрасывать; старый маркер `channel_import` не используется. Если включённых каналов нет, сборщик не обращается к Telegram. Env остаётся для реквизитов и общих настроек.

Реализация: [channels.py](tg_event/channels.py), [схема и прогресс](tg_event/database.py), [сборщик](tg_event/collector.py), [цикл watcher](tg_event/cli.py). Проверки без реальных запросов: `python3 -m unittest discover -s tests -p test_channels.py`.

### Схема SQLite

Таблицы: `sources`, `raw_posts`, `post_links`, `events`, `event_sources`, `event_field_locks`. `event_sources` хранит связи события с постами и извлечённые сведения отдельно от полей карточки; у старых записей исходное извлечение неизвестно (NULL). `events.raw_post_id` указывает на основной пост. `event_field_locks` защищает ручные изменения и поля старых карточек с неизвестной историей. Связи по `source_id`, `raw_post_id` и `event_id`, `ON DELETE CASCADE`, `PRAGMA foreign_keys = ON`. Запись — upsert по `(source, message_id)`; ссылки поста заменяются, карточки больше не удаляются при повторном разборе. Совпадения объединяются через связи источников; автоматически дополняются только незаполненные незащищённые поля, статус сохраняется.

Watcher также использует `watch_progress`: позиция и начальная дата по каналу и полному пути `--state`. Результаты пакета и позиция фиксируются одной транзакцией. Старый JSON импортируется при создании профиля, затем служит вспомогательной копией. Watcher читает самые ранние непройденные сообщения порциями, `--since` задаёт начальную границу нового канала. Постоянный цикл повторяет попытки после ошибки; `--once` сообщает о неуспешном канале/посте после сохранения успешных результатов. Постоянно неразбираемый пост задерживает свой канал; прежние пропуски позади импортированной позиции не восстанавливаются автоматически. При очистке сохранять прогресс.

Веб-админка по умолчанию показывает исключения (draft или конфликт), дополнительно доступен фильтр конфликтов. Ручное редактирование включает event_state. Закрытие конфликта записывает последнюю проверенную версию поста в event_conflict_resolutions (каскадное удаление вместе с карточкой); новая версия может снова потребовать проверки. Объединение сохраняет выбранную карточку и присоединяет источники, фиксируя различающиеся поля и сохраняя ручные блокировки. Объединение карточек с общим постом запрещено, чтобы не потерять извлечения. Интерфейс и ограничения описаны в этапе 7 PLAN.md.

Views (для удобства модерации в GUI):
- `events_for_review` — только `draft`, последние сверху.
- `events_current` — `published` в состоянии `scheduled` с датой >= сегодня.
- `events_outdated` — все события с прошедшей датой.

### Статусы и категории

- Состояние мероприятия (`event_state`) хранится отдельно от статуса публикации: `scheduled`, `postponed` (перенесено без даты), `cancelled`. В боте видны только scheduled; отмены и переносы без даты скрываются. Хранятся прежняя дата, время/источник последнего подтверждённого изменения и ссылка на спорное сообщение, без журнала версий. Эти служебные поля удаляются вместе с карточкой при очистке через 30 дней; будущие события и нужные им посты сохраняются. Правила — этап 9 PLAN.md.

- Новые распарсенные события с названием и корректной датой (или диапазоном дат) получают `published`; при недостаточных сведениях — `draft`. Время, место и цена необязательны. Модератор может изменить статус, включая `rejected`. Пост без события обычно даёт пустой список событий; объект с `is_event=false` получает `not_event`. Повтор уже существующего события → `repeat` (не виден в боте).
- В командах parse/run/watch новые карточки с завершившимся до сегодняшнего дня диапазоном не сохраняются. Сегодня определяется по EVENT_TIMEZONE, окончание — end_date, иначе date; сегодняшний день включён. Ограничение применяется в транзакции после сопоставления всего пакета, поэтому старый анонс с переносом на будущую дату сохраняет будущую карточку. Обновления существующих карточек обрабатываются, ранее сохранённые карточки этим правилом не удаляются. Неизвестные/невалидные даты остаются черновиками. Сырой пост сохраняется как обработанный, прогресс продвигается; отладочная выгрузка может содержать исходные извлечения отсеянных событий. Низкоуровневый save_parsed_rows принимает явный not_before; CLI передаёт текущую дату города.
- Дедупликация и сопоставление изменений: один LLM-запрос на пакет к fallback-модели, когда есть кандидаты в базе или несколько новых событий. Учитываются совпадения внутри пакета. Для обычных анонсов используются текущие и известные прежние даты, для изменений — также актуальные и недавние события. repeat/not_event не берутся как оригиналы; отклонённые учитываются. Совпадение связывается с оригиналом без отдельной карточки. Основной источник выбирается по `source_rules.json` (путь `SOURCE_RULES_PATH`), затем по полноте и дате поста; реальные связи каналов пока не заполнены.
- Допустимые категории: `music, cinema, lecture, exhibition, market, workshop, food, sport, party, kids, other`.

### Бот

- `tg_event/bot.py` — бот на Telethon (отдельная сессия `tg_event_bot`, токен `BOT_TOKEN`).
- Команды: `/start` (inline-кнопки: сегодня / завтра / неделя / месяц), `/help`.
- Бот показывает только события со статусом `published` и состоянием `scheduled` в выбранном диапазоне дат. Конфликт отображается предупреждением и ссылкой на сообщение. Watcher повторно разбирает изменённые посты; сборщик отдельно запрашивает посты, связанные с актуальными/недавними событиями, вне обычного окна последних сообщений. Удаление поста не считается автоматической отменой.
- Дни в выдаче бота считаются по EVENT_TIMEZONE (имя IANA, по умолчанию Asia/Vladivostok), независимо от сервера и устройства. Неделя и месяц — следующие 7 и 30 дней, включая сегодня. Многодневные события отбираются по пересечению с периодом и показываются один раз под первым днём пересечения, с полным диапазоном в карточке. Город по умолчанию — Владивосток; CITY и EVENT_TIMEZONE задаются независимо.
- Бот и watcher запускаются в одном asyncio-процессе командой `watch` (кроме `--once` — там только цикл watcher, без бота).

## Команды

Установка окружения:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Запуск (нужен `.env`, см. `.env.example`):

```bash
python -m tg_event.cli collect
python -m tg_event.cli parse --input data/raw/posts-YYYYMMDD-HHMMSS.jsonl
python -m tg_event.cli run
python -m tg_event.cli watch
python -m tg_event.cli watch --once
python -m tg_event.cli cleanup
python -m tg_event.cli cleanup --apply
```

cleanup без --apply — только просмотр, без миграции и удаления; Telegram/LLM-реквизиты не нужны. Перед удалением сохраняется одна резервная копия базы и удаляемых выгрузок в backups/cleanup-latest.zip рядом с базой. Watcher проверяет недельное расписание после успешного цикла; прогресс watcher не удаляется. events.updated_at обновляется триггерами только при содержательных правках, не при пустом повторном разборе. Состояние расписания — maintenance_state. Секретные env-файлы не открывать для проверки этих команд; в тестах load_dotenv подменяется.

Тесты (только стандартная библиотека):

```bash
python3 -m unittest discover -s tests
```

Типа-чек и линтер в проекте не настроены — для проверки используй тесты выше.

## Поведение агента

Смещение баланса в сторону осторожности, а не скорости. Для тривиальных задач — используй здравый смысл.

### 1. Думай перед кодом

**Не предполагай. Не прячь сомнения. Озвучивай tradeoff.**

- Формулируй предположения явно. Если не уверен — спроси.
- Если есть несколько интерпретаций — предъяви их, не выбирай молча.
- Если видишь более простой путь — скажи. Возражай, когда уместно.
- Если что-то непонятно — остановись, назови, что именно, спроси.

### 2. Сначала простота

**Минимум кода, решающий задачу. Ничего спекулятивного.**

- Без фич сверх запрошенного.
- Без абстракций для однократного использования.
- Без «гибкости» и «настраиваемости», которых не просили.
- Без обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Вопрос к себе: «Сказал бы senior-инженер, что это overcomplicated?» Если да — упрощай.

### 3. Хирургические правки

**Трогай только то, что нужно. Чисти только за собой.**

- Не «улучшай» соседний код, комментарии, форматирование.
- Не рефактори то, что не сломано.
- Следуй существующему стилю, даже если сделал бы иначе.
- Заметил неродной мёртвый код — упомяни, не удаляй.
- Твои изменения создали orphan-импорты/переменные — удали только их. Pre-existing dead code не трогай без запроса.

Тест: каждая изменённая строка должна прямо追溯到 задаче пользователя.

### 4. Целевое исполнение

**Определи критерий успеха. Крути, пока не проверишь.**

Преобразуй задачи в верифицируемые цели:
- «Добавить валидацию» → «Напиши тесты для невалидных входов, сделай так, чтобы они проходили».
- «Починить баг» → «Напиши тест, воспроизводящий его, потом почини».
- «Рефактор X» → «Тесты проходят до и после».

Для многошаговых задач — краткий план:
```
1. [Шаг] → проверка: [что проверить]
2. [Шаг] → проверка: [что проверить]
3. [Шаг] → проверка: [что проверить]
```

Сильный критерий успеха позволяет крутиться автономно. Слабый («сделай, чтоб работало») требует постоянных уточнений.

## Проектные конвенции

- **План работ и промежуточная приёмка:** для задач развития агрегатора используй [PLAN.md](PLAN.md). Выполняй только выбранный пользователем этап, фиксируй результат и останавливайся для проверки; не переходи к следующему автоматически.

- **Будущая обработка дублей и обновлений:** перед задачами о дедупликации, выборе основного источника, переносах и отменах прочитай [EVENT_DUPLICATES.md](EVENT_DUPLICATES.md). Там зафиксированы целевое поведение и открытые вопросы; это не описание текущей реализации и не поручение реализовать всё сразу.

- **Без новых Python-зависимостей.** В `requirements.txt` только `telethon`. Всё остальное — стандартная библиотека. Если задача требует новой зависимости — обсуди.
- **Исключение — админ-фронтенд `admin-ui/`.** Это Vue 3 + Vite + Pinia + Vuestic UI с оболочкой и темой из Vuestic Admin на Node-тулчейне. Единственное место в репо, где допускаются npm-зависимости и билд-степ. Запускается командой `serve` (`python -m tg_event.cli serve`); для прода нужен `cd admin-ui && npm run build` (собранный `dist/` отдаётся тем же Python-сервером, `dist/` в git не коммитится). Python-сторона админки (`tg_event/admin.py`, `tg_event/auth.py`) — stdlib-only.
- **Без сторонних `.env`-парсеров.** Используй существующую `load_dotenv` из `tg_event/config.py`.
- **Стиль:** `from __future__ import annotations`, dataclasses для конфигов, `Path` для путей, type hints.
- **Комментарии:** не добавляй комментарии, если явно не просят.
- **Коммиты:** не делай коммитов, если пользователь явно не попросил. Не пушь и не создавай PR без запроса.
- **Секреты:** никогда не логируй и не коммить ключи/токены. Существующий `.env.example` содержит настоящие секреты — это надо поправить отдельно (не частью текущей задачи).
